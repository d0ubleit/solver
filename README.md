> Telegram-бот, который не просто хранит задачи, а **проактивно помогает решать проблемы**:
> анализирует ситуацию через LLM, разбивает на конкретные шаги, ведёт диалог-сессию
> и напоминает о прогрессе.

В отличие от обычных todo-трекеров (которые пассивно ждут, пока вы что-то впишете), Solver
работает как личный AI-коуч: вы описываете проблему своими словами, а он задаёт уточняющие
вопросы, формирует план действий и мягко сопровождает вас до результата.

## Демонстрация

Пример реального диалога с ботом:

```
👤 /new
🤖 Опиши свою проблему или задачу одним предложением.

👤 Хочу полететь с семьёй на море
🤖 Теперь расскажи подробнее. Что именно происходит? Чем больше деталей — тем точнее анализ.

👤 Нужен тур в 5* отель, всё включено
🤖 🔍 Анализирую проблему...
🤖 ⚡ Хочу полететь с семьёй на море
   📋 Шаги (0/5):
     1. Определите бюджет (мин/макс) на всех
     2. Выберите примерные даты и продолжительность
     3. Уточните предпочтения по направлению
     4. Укажите количество человек и возраст детей
     5. Проверьте чек-лист: паспорта, страховка, бронь
   💬 Ты в сессии этой проблемы. Пиши — я помогу уточнить шаги.

👤 1. Бюджет 250–350 тыс. 2. Вылет 26–28 июля. 3. Турция. 4. 2 взрослых + ребёнок 5 лет
🤖 Отлично! Теперь можно искать туры. Уточните: важна ли анимация для ребёнка?

👤 Важно, чтобы были реальные хорошие отзывы
🤖 Понял. Вот на что обратить внимание при выборе отеля...
```

Бот **ведёт диалог в контексте проблемы**, задаёт уточняющие вопросы разом,
корректирует рекомендации по ходу общения и адаптирует стратегию под тип задачи.

## Ключевые возможности

| Возможность | Описание |
|-------------|----------|
| 🧠 **AI-анализ проблем** | LLM декомпозирует проблему на 3-5 конкретных шагов (DeepSeek / любой OpenAI-совместимый API) |
| 💬 **Сессии-диалоги** | Каждая проблема — это сессия: можно задавать вопросы, уточнять и корректировать план |
| 🎯 **Умная маршрутизация промптов** | Проблема классифицируется по категории (карьера, конфликты, здоровье, путешествия) → подбирается специализированный промпт |
| ⏰ **Проактивные напоминания** | Планировщик периодически генерирует персональные чек-ины и напоминает о прогрессе |
| ✅ **Трекинг прогресса** | Отметка шагов, проценты выполнения, авто-закрытие проблемы при завершении всех шагов |
| 🔄 **Восстановление контекста** | История диалога хранится в БД — бот помнит, о чём вы говорили |
| 🩺 **Self-diagnostics** | Команда `/test` — встроенные проверки работоспособности прямо в чате |
| 🧪 **Scriptable self-testing** | Команда `/run_test` прогоняет сценарий `/new\|текст\|/list\|/done 1 1` и выдаёт отчёт |

## Архитектура

Проект построен по принципам **Clean Architecture** и **SOLID** с чётким разделением
на слои и инверсией зависимостей (внутренние слои не знают о внешних).

```
┌──────────────────────────────────────────────────────────┐
│  Presentation  ·  Telegram handlers, MarkdownV2 validator  │
├──────────────────────────────────────────────────────────┤
│  Application   ·  ProblemService, AIAnalysis, PromptService│
├──────────────────────────────────────────────────────────┤
│  Domain        ·  Entities, Value Objects, Repository ABCs │
├──────────────────────────────────────────────────────────┤
│  Infrastructure·  SQLAlchemy, OpenAI client, APScheduler   │
└──────────────────────────────────────────────────────────┘
          Зависимости направлены ВНУТРЬ (к домену)
```

**Слои:**

- **Domain** — чистая бизнес-логика: сущности (`Problem`, `SolutionStep`, `User`,
  `ConversationContext`, `PromptTemplate`), value objects (`ProblemStatus`, `Priority`,
  типизированные ID), интерфейсы репозиториев. Не зависит ни от одного фреймворка.
- **Application** — сценарии использования: `ProblemService` (CRUD + оркестрация AI),
  `AIAnalysisService` (абстракция над LLM), `PromptService` (маршрутизация промптов), DTO на Pydantic.
- **Infrastructure** — адаптеры: SQLAlchemy-репозитории, клиент LLM, планировщик APScheduler.
- **Presentation** — Telegram-обработчики, валидатор разметки.

**Принципы:**
- **Dependency Inversion**: домен зависит от абстракций (`AIAnalysisService`,
  `ProblemRepository`), а не от реализаций → LLM и БД заменяемы без изменения бизнес-логики.
- **Repository Pattern**: персистентность скрыта за интерфейсами.
- **Rich Domain Model**: инварианты (нельзя закрыть уже закрытую проблему, нельзя выполнить
  шаг дважды) защищены внутри сущностей и покрыты тестами.

## Инженерные решения

Проект интересен не только фичами, но и **реальными задачами, которые пришлось решать**.
Этот раздел — витрина инженерного мышления.

### 1. Валидатор Telegram MarkdownV2

Telegram MarkdownV2 очень капризен: символы `.`, `!`, `-`, `(`, `)` и ещё десяток
зарезервированы и должны экранироваться **везде**, даже внутри форматирования. LLM генерирует
текст с точками в нумерованных списках → бот падает с `Can't parse entities`.

**Решение:** собственный валидатор (`markdown_validator.py`), который находит
неэкранированные зарезервированные символы, игнорируя легитимные пары форматирования
(`*bold*`, `_italic_`, `` `code` ``). Плюс **универсальный набор тестов**, который прогоняет
через валидатор ВСЕ типы сообщений бота до коммита.

### 2. Устойчивый парсинг JSON от LLM

LLM (DeepSeek) иногда возвращает почти-JSON: с лишними символами, обрезанный или обёрнутый
в текст. Наивный `json.loads()` падает.

**Решение:** трёхуровневый fallback — (1) прямой парсинг → (2) извлечение подстроки между
первой `{` и последней `}` и повторная попытка → (3) использование сырого текста как ответа.
Бот никогда не «падает» из-за капризов модели.

### 3. Динамическая маршрутизация промптов

Один системный промпт плохо работает для всего спектра проблем (карьера ≠ путешествия ≠
конфликты).

**Решение:** `PromptService` классифицирует проблему по ключевым словам → подбирает
специализированный seed-промпт (career / conflict / health / travel / general) → инкрементирует
счётчик использования. Архитектура готова к замене keyword-классификации на LLM-based и к
авто-генерации новых промптов (см. Roadmap).

### 4. Сессии как агрегаты диалога

Проблема — это не просто запись в БД, а **живая сессия** с историей диалога. `ConversationContext`
хранит сообщения и время последней активности. `continue_dialog()` передаёт LLM историю +
текущие шаги, а модель может вернуть обновлённый план (`updated_steps`).

### 5. Управление порядком хендлеров и фильтрами

Свободный текст в сессии не должен мешать командам и потоку `/new`. Решено корректным
порядком регистрации хендлеров (`ConversationHandler` раньше catch-all `MessageHandler`) и
фильтрами PTB (`filters.TEXT & ~filters.COMMAND`).

## Тестирование

Проект разработан по **TDD** (Red → Green → Refactor). **139 тестов**, покрытие **70%**
(доменный слой — 95-97%).

```
tests/
├── unit/          # сущности, value objects, сервисы (с моками), промпты, валидатор
├── integration/   # репозитории против реальной in-memory SQLite
└── e2e/           # полный путь: Telegram Update → handler → service → БД → ответ
```

**Что покрыто:**
- ✅ Доменные сущности и их инварианты (переходы статусов, прогресс, ошибки)
- ✅ Сервисы с замоканными репозиториями и LLM
- ✅ Репозитории против настоящей БД (in-memory SQLite)
- ✅ E2E-сценарии через фейковый Telegram (`FakeBot`): `/new`, `/list`, `/view`, `/done`, сессии
- ✅ Валидация MarkdownV2 для всех типов сообщений

**Запуск:**
```bash
pytest tests/ --cov=solver --cov-report=term-missing
```

**Дополнительно — самодиагностика прямо в чате:**
- `/test` — 5 встроенных проверок работоспособности
- `/run_test /new|Моя проблема|/skip|/list|/view 1|/done 1 1` — сценарный прогон

## Быстрый старт

### Требования
- Python 3.11+ или Docker
- Токен бота от [@BotFather](https://t.me/BotFather)
- API-ключ LLM ([DeepSeek](https://platform.deepseek.com) или OpenAI)

### Через Docker (рекомендуется)

```bash
# 1. Настроить окружение
cp .env.example .env
# → отредактировать .env: TELEGRAM_BOT_TOKEN и AI_API_KEY

# 2. Собрать и запустить
docker compose up -d --build

# 3. Логи
docker compose logs -f
```

### Локально (для разработки)

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
cp .env.example .env          # заполнить токены
python -m solver.main
```

### Переменные окружения (`.env`)

```bash
TELEGRAM_BOT_TOKEN=your_token
AI_API_KEY=your_key
AI_BASE_URL=https://api.deepseek.com      # или https://api.openai.com/v1
AI_MODEL=deepseek-chat                    # или gpt-4o-mini
DATABASE_URL=sqlite+aiosqlite:///solver.db
PROACTIVE_CHECK_INTERVAL_MINUTES=60
```

## Ограничения и Roadmap

Проект — **production-grade MVP** с честно очерченными границами. Ниже — что осознанно
вынесено за скоуп и куда двигаться дальше.

**Текущие ограничения:**
- 🔸 LLM **не имеет доступа в интернет** — не ищет актуальные цены/ссылки (нужна интеграция
  web-search API: SerpAPI / Brave Search)
- 🔸 Классификация промптов — по ключевым словам (MVP), не семантическая
- 🔸 Активные сессии живут в памяти процесса (история в БД сохраняется, но активная сессия
  теряется при рестарте)
- 🔸 Схема БД создаётся автоматически; миграции (Alembic) — в планах

**Roadmap:**
- [ ] Интеграция web-search (реальные туры, ссылки, цены)
- [ ] LLM-based классификация проблем + авто-генерация новых промптов
- [ ] Перенос активных сессий в БД + TTL/таймаут
- [ ] Alembic-миграции
- [ ] 👍/👎 обратная связь на ответы → деактивация плохих промптов
- [ ] Персонализация проактивности (уровень «настойчивости»)
