# План: Сессии и Динамические промпты (3 итерации критики)

## Пункт 2: Проблема = Сессия

### Итерация 1 — Первичный дизайн

**Концепт:**
После создания проблемы через `/new`, пользователь может продолжить диалог в
контексте этой проблемы. Бот хранит историю в `ConversationContext`, и
каждое новое сообщение пользователя (не-команда) идёт как часть диалога.

**Механика:**
- `/new` создаёт проблему → AI-анализ → шаги → бот входит в "режим сессии"
- В сессии: любое сообщение = вопрос/уточнение по проблеме
- AI видит всю историю (`ConversationContext.messages`) + шаги + анализ
- AI отвечает текстом, может предложить обновить/добавить шаги
- `/leave` — выйти из сессии
- `/session N` — войти в сессию проблемы N (если нужно переключиться)

**Уточняющие вопросы ДО анализа:**
- Если в `/new` пользователь дал мало информации, AI вместо шагов возвращает
  список уточняющих вопросов
- Пользователь отвечает — AI доанализирует с новыми данными
- Цикл: вопрос → ответ → вопрос → ... → готово, создаём шаги

**Данные:**
- `ConversationContext` уже есть (id, problem_id, messages, summary, tokens_used)
- Добавить поле `status`: GATHERING_INFO | ACTIVE | CLOSED
- Добавить связь с `Problem` для быстрого доступа к "активной сессии"

### Итерация 2 — Критика

**Что упущено:**
1. **Смена проблемы во время сессии.** Если пользователь говорит "кстати, ещё
   другая проблема...", бот должен распознать это и предложить /new, а не
   пытаться прилепить к текущей сессии.
2. **Ручной выход.** `/leave` есть, но что если пользователь просто
   перестал отвечать? Нужен таймаут сессии (например, 30 мин бездействия).
3. **Контекст раздувается.** При длинных диалогах `messages` растёт,
   токены дорожают. Нужна авто-суммаризация каждые N сообщений.
4. **Конкуренция команд.** Если пользователь в сессии и пишет `/list` —
   команда должна работать, а не уходить в диалог. Все `/`-сообщения = команды.
5. **Несколько одновременных проблем.** Пользователь может иметь 3 активные
   проблемы и переключаться между ними. Нужен явный `/session N`.
6. **AI не обновляет шаги.** Сейчас `analyze()` создаёт шаги ОДИН раз.
   В сессии AI должен иметь возможность: добавить шаг, удалить шаг,
   переформулировать шаг, отметить как неактуальный.

**Что лишнее:**
- Поле `status` на ConversationContext избыточно — статус можно вывести
  из статуса самой Problem (draft → analyzing → active → resolved).
- Отдельная команда `/session N` — можно упростить: `/view N` автоматически
  входит в сессию этой проблемы.

### Итерация 3 — Финальный дизайн

**Итоговая механика:**
1. `/new` → сбор информации (возможно несколько раундов) → AI-анализ → шаги
2. После создания — бот в сессии последней созданной проблемы
3. Любое не-команда сообщение → AI.continue_dialog()
4. `/view N` → показывает проблему и входит в её сессию
5. Все `/`-команды работают как обычно
6. AI в сессии может: ответить текстом, обновить шаги, задать вопрос
7. Таймаут сессии: 30 мин → авто-выход с сообщением
8. Суммаризация: при >20 сообщений в контексте — сжать до саммари

**API AI (новые методы):**
- `analyze(problem, conversation_history)` → steps OR clarifying_questions
- `continue_dialog(problem, steps, conversation_history, user_message)` →
  {reply, updated_steps?, new_question?}
- `summarize_context(messages)` → краткое саммари

**Изменения в данных:**
- `ConversationContext`: добавить `last_activity_at`
- `Problem`: добавить связь `active_session_user_id` (опционально — для
  отслеживания кто в сессии)

## Пункт 3: Динамические промпты

### Итерация 1 — Первичный дизайн

**Концепт:**
Система шаблонов промптов, которые подбираются под категорию проблемы,
адаптируются LLM под конкретную ситуацию, и создаются на лету для новых
категорий.

**Сущности:**
- `PromptTemplate`: id, category, title, system_prompt, clarifying_questions
  (JSON list), step_schema (JSON), usage_count, success_score, created_at
- `PromptRepository`: CRUD + find_by_category + find_similar (семантически)

**Поток:**
1. Пользователь описывает проблему
2. `PromptRouter.classify(problem_text)` → категория (travel, health, career,
   conflict, finance, general)
3. `PromptRepository.find_by_category(category)` → шаблон или None
4. Если найден: LLM адаптирует `{system_prompt}` под конкретику проблемы
5. Если не найден: LLM генерирует новый шаблон → сохраняем → используем
6. Адаптированный промпт используется для анализа

**Категории (начальные):**
- `travel` — поездки, билеты, отели
- `career` — работа, карьера, собеседования
- `health` — здоровье, спорт, питание
- `finance` — деньги, бюджет, инвестиции
- `conflict` — конфликты, отношения
- `education` — обучение, курсы
- `tech` — технические проблемы
- `general` — всё остальное (дефолтный промпт)

### Итерация 2 — Критика

**Что упущено:**
1. **Холодный старт.** При первом запуске нет шаблонов. Нужны "seed"-шаблоны
   для 5-7 основных категорий, зашитые в код или миграцию.
2. **Качество авто-сгенерированных шаблонов.** LLM может сгенерировать
   плохой промпт. Нужна валидация: после создания шаблона — тестовый прогон
   на 2-3 синтетических проблемах этой категории. Если ответы некачественные
   — шаблон помечается как "draft" и не используется.
3. **Зацикливание.** Если шаблон плохой, LLM может адаптировать его ещё хуже.
   Нужен `min_usage_count` перед тем как шаблон участвует в адаптации других.
4. **Семантический поиск vs категории.** Жёсткие категории не покрывают
   пограничные случаи ("карьерный конфликт" — career или conflict?).
   Нужен embedding-based similarity search как дополнение к категориям.
5. **Стоимость.** Каждый вызов LLM для классификации + адаптации + анализа
   — это 2-3 запроса вместо 1. Для MVP можно объединить классификацию и
   адаптацию в один вызов.
6. **Обратная связь.** Пользователь должен иметь возможность оценить
   качество ответа (👍/👎) — это влияет на `success_score` шаблона.
7. **Версионирование.** Если шаблон адаптировался 50 раз, он "дрейфует"
   от исходного. Нужно хранить историю версий или периодически
   "пересоздавать" шаблон из накопленного опыта.

**Что лишнее:**
- `step_schema` в шаблоне — избыточно, LLM сам определит структуру шагов.
- `success_score` — преждевременно без реальных пользователей.
  Заменяем на `usage_count` + флаг `is_verified`.
- Полноценный embedding-поиск для MVP — дорого (нужна векторная БД).
  Вместо этого: keyword matching + LLM-классификация.

### Итерация 3 — Финальный дизайн

**MVP-скоуп (без переусложнения):**
1. **Seed-шаблоны:** 5 вшитых промптов (general, career, conflict, health, travel)
2. **Классификация:** один вызов LLM, который возвращает `{category, adapted_prompt}`
   — и классифицирует, и адаптирует за один запрос
3. **Новые шаблоны:** если LLM считает что категория новая — возвращает
   `{category: "new:...", adapted_prompt: "...", suggested_title: "..."}`.
   Сохраняем в БД для будущего использования.
4. **Поиск:** точное совпадение по category, иначе — general
5. **Обратная связь:** 👍/👎 кнопки на ответе. `usage_count++`.
   При 3👎 подряд — шаблон деактивируется.
6. **Никаких embedding'ов, версионирования, валидации шаблонов** — это v2.

**Сущности (MVP):**
```
PromptTemplate:
  id: UUID
  category: str (unique index)
  title: str
  system_prompt: str (full prompt text)
  usage_count: int (default 0)
  is_active: bool (default true)
  created_at: datetime
```

**API AI (новый метод):**
- `classify_and_adapt(problem_title, problem_description, base_prompt)`
  → `{category, adapted_prompt, is_new_category, suggested_title?}`

**Поток (упрощённый):**
1. Пользователь: "Нужна горящая путёвка в Турцию"
2. `PromptRepository.find_by_category("travel")` → найден seed-шаблон
3. `AI.classify_and_adapt(title, desc, template.system_prompt)` →
   `{category: "travel", adapted_prompt: "...уточни бюджет и даты..."}`
4. Адаптированный промпт + проблема → `AI.analyze()` → шаги
5. Если бы шаблон не нашёлся → `AI.classify_and_adapt(..., general_prompt)` →
   `{category: "new:pet_care", adapted_prompt: "...", suggested_title: "Уход за
   питомцами"}` → сохраняем новый шаблон → используем

## План реализации (последовательность)

### Этап A: Сессии (п.2)
1. Расширить `AIAnalysisService`: добавить `continue_dialog()` и
   `gather_clarifications()` (двухфазный анализ)
2. Обновить `ConversationContext`: добавить `last_activity_at`
3. Добавить в `ProblemService`: `continue_session()`, `get_active_session()`
4. Добавить в `BotHandlers`: session mode, `/leave`, авто-вход в сессию
5. Таймаут сессии: проверка в `list_problems` или отдельный job
6. Суммаризация контекста при >20 сообщений
7. Тесты (E2E: сессия → диалог → уточнение → обновление шагов)

### Этап B: Динамические промпты (п.3)
1. Создать `PromptTemplate` entity + DB model + repository
2. Seed-миграция: 5 встроенных шаблонов
3. `PromptService`: classify + adapt + create_new
4. Интегрировать в `ProblemService.analyze_problem()`: перед анализом —
   подобрать/адаптировать промпт
5. Кнопки 👍/👎 на ответах с шагами
6. Обработка фидбека: `usage_count++`, деактивация при 3👎
7. Тесты

### Что НЕ делаем в этом этапе:
- Embedding-поиск
- Версионирование шаблонов
- Валидация шаблонов тестовыми прогонами
- Мульти-категорийные проблемы (только одна категория)
